Writing a SQL parser: dev log

2026-08-01

After finishing the KV store, I wanted to try something closer to compilers. Writing a SQL parser seemed like a good middle ground — not a full compiler, but enough to understand lexing, parsing, and tree evaluation.

Day 1: Tokenizer

Started with regex. It worked for simple cases: SELECT, FROM, WHERE, identifiers, numbers. But then I tested a string with a comma inside it:

INSERT INTO t (name) VALUES ('hello, world')

The comma inside the string got treated as a separator. Regex doesn't track state well across matches. Scrapped it and wrote a manual state machine.

The state machine approach is simpler than it sounds. You maintain a position pointer and a current character. At each step you ask: is this whitespace? a digit? a letter? a quote? Then consume accordingly. The tricky part is multi-character operators (>=, <=, <>) where you need one character of lookahead.

Day 2: Parser

Recursive descent seemed like the natural approach. Each grammar rule gets its own function. When you call parse_select(), it expects SELECT, then a column list, then FROM, then a table name, and so on.

Operator precedence was the main design decision. In SQL, AND binds tighter than OR, and comparisons bind tighter than both. The solution: encode precedence in function call depth.

parse_expression -> parse_or -> parse_and -> parse_comparison -> parse_atom

Each level calls the next tighter level and then loops on its own operator. So parse_or calls parse_and and then loops on OR tokens. parse_and calls parse_comparison and loops on AND. This naturally gives the right precedence without an explicit precedence table.

Day 3: Execution engine

The table model is straightforward: a dict keyed by column name for each row. WHERE evaluation walks the AST recursively.

ORDER BY was harder than expected. Different data types (int, str, None) can't be compared directly — Python throws TypeError. The fix: wrap sort keys in a tuple: (type_priority, value). None gets priority 1 (sorts last), everything else gets priority 0. This cleanly separates type groups before value comparison.

What I learned

  • Regex is fine for simple tokenizing, breaks down when state matters
  • Recursive descent is intuitive once you map grammar rules to functions
  • Operator precedence comes for free from call hierarchy
  • AST evaluation is basically tree traversal — every node type has an eval method
  • Real SQL engines add query optimization between parsing and execution; mine skips that entirely

The result: a SQL engine that actually runs SELECT, INSERT, CREATE, DELETE with WHERE, ORDER BY, and LIMIT. Not production-grade, but enough to understand the fundamentals.
