写一个 SQL 解析器的开发日志

2026-08-01

写完 KV 存储之后，想试试更接近编译器的东西。写个 SQL 解析器感觉是个不错的中间地带——不需要完整的编译器，但能理解词法分析、语法分析和 AST 求值。

第一天: 词法分析器

一开始用正则表达式。简单的 SQL 能过：SELECT、FROM、WHERE、标识符、数字。然后测了一个带逗号的字符串：

INSERT INTO t (name) VALUES ('hello, world')

字符串里的逗号被当成了分隔符。正则表达式不跟踪状态——它不知道当前是不是在字符串里面。果断放弃正则，改用手写状态机。

状态机的思路其实很简单：维护一个位置指针和当前字符，每步看：这是空白？数字？字母？引号？然后相应地消费字符。多字符操作符(>=、<=、<>)需要一个字符的预读。

第二天: 语法分析器

选用了递归下降法。每个语法规则对应一个解析函数。parse_select() 期望 SELECT、列列表、FROM、表名依次出现。

运算符优先级是最主要的设计决策。在 SQL 中，AND 比 OR 优先级高，比较运算符比两者都高。解决方案是用函数调用深度来编码优先级：

parse_expression -> parse_or -> parse_and -> parse_cmp -> parse_atom

每层调用下一层更紧的函数，然后在本层的运算符上循环。parse_or 调用 parse_and 然后在 OR 上循环，parse_and 调用 parse_cmp 然后在 AND 上循环。这样优先级自然就对了，不需要显式的优先级表。

第三天: 执行引擎

表的数据模型很简单：每行是一个 dict，列名做 key。WHERE 求值就是递归遍历 AST——ColumnRef 从当前行取值，Literal 返��常量，BinaryOp 左右子树递归求值然后运算。

ORDER BY 比预想的难。不同类型的数据不能直接比较——Python 会抛 TypeError。解决方案是用 (type_priority, value) 元组包装排序键：NULL 排最后(priority=1)，其他值排前面(priority=0)。这样不同类型之间也能安全比较。

收获

  • 正则适合简单场景，一旦涉及状态(字符串内部、嵌套注释)就不够用了
  • 递归下降很直观，语法规则映射到函数，运算符优先级靠调用深度
  • AST 求值本质是树遍历，每种节点类型有自己的求值逻辑
  • 真正的 SQL 引擎在解析和执行之间还加了查询优化层，我这个直接跳过了
