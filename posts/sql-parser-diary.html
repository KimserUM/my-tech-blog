Writing a SQL Parser: Dev Log

2026-08-01

After the KV store, wanted something closer to compilers. A SQL parser seemed like a good middle ground — parse text, build a tree, evaluate the tree.

Day 1: Tokenizer

Started with regex. Fine for simple cases: SELECT, FROM, identifiers, numbers. Then tested a string with a comma:

INSERT INTO t (name) VALUES ('hello, world')

The comma inside the string was treated as a separator. Regex doesn't track state across matches. Replaced with manual FSM.

The FSM: maintain position pointer, check current char: whitespace? digit? letter? quote? Consume accordingly. Multi-char operators (>=, <=, <>) need one char of lookahead.

Day 2: Parser

Recursive descent: each grammar rule = one function. parse_select() expects SELECT, column list, FROM, table name.

Operator precedence via function depth:

parse_expression -> parse_or -> parse_and -> parse_cmp -> parse_atom

parse_or calls parse_and, loops on OR. parse_and calls parse_cmp, loops on AND. Precedence is free from the call hierarchy.

Day 3: Engine

Table model: dict of dicts. WHERE walks AST recursively. ORDER BY required (type_priority, value) tuples because different types can't compare directly in Python.

What I learned

  • Regex is fine until state matters
  • Recursive descent maps grammar rules to functions naturally
  • Operator precedence is encoded in call depth
  • AST evaluation is tree traversal
