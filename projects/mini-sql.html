mini-sql

Python | tokenizer | recursive descent parser | execution engine | ~1100 lines | 2026.07-08

What it does

A miniature SQL database engine with three stages: lexer converts SQL text to tokens, parser builds an AST from tokens, engine executes the AST on in-memory tables. No external dependencies for the core logic.

Pipeline

SQL string
  -> Tokenizer (hand-written state machine)
  -> Token stream
  -> Parser (recursive descent)
  -> AST
  -> Engine (tree-walking interpreter)
  -> Result (rows / status messages)

Stage 1: Tokenizer

Hand-written finite state machine. Main states: whitespace skip, number (digits + optional decimal), word (alphanumeric + underscore, checked against keyword table), string (single-quote delimited), operator (single or double character). Comments (--) are skipped.

Keywords: SELECT, FROM, WHERE, INSERT, INTO, VALUES, CREATE, TABLE, DELETE, AND, OR, ORDER, BY, ASC, DESC, LIMIT.

Stage 2: Recursive Descent Parser

Each grammar rule maps to one parse function. Operator precedence is encoded via call hierarchy:

parse_expression()
  -> parse_or()        // handles OR
    -> parse_and()     // handles AND
      -> parse_comparison()  // handles =, <, >, <=, >=, <>
        -> parse_atom()      // column ref, literal, (expr)

Stage 3: Execution Engine

Tables stored as dict of dicts. Columns as a list of ColumnDef (name + type). Rows as a list of dicts (one dict per row).

WHERE evaluation walks the expression AST recursively: ColumnRef looks up the value from the current row, Literal returns its value, BinaryOp evaluates left and right subtrees then applies the operator.

Type conversion happens at INSERT time (INT to int, FLOAT to float, NULL handling). ORDER BY casts values to (type_sort, value) tuples so different types sort together without error.

Supported SQL

CREATE TABLE users (id INT, name STRING, age INT);

INSERT INTO users (id, name, age) VALUES (1, 'tom', 20);
INSERT INTO users (id, name, age) VALUES (2, 'alice', 22);

SELECT * FROM users;
SELECT name, age FROM users WHERE age >= 20;
SELECT * FROM users WHERE name = 'tom' AND age > 18;
SELECT * FROM users ORDER BY age DESC LIMIT 5;

DELETE FROM users WHERE id = 3;

Things not supported (on purpose)

JOIN, subqueries, GROUP BY, UPDATE, indexes, transactions. These would require a query planner and more complex execution model, beyond the scope of understanding the fundamentals.

Problems solved

  • Regex tokenizer broke on strings containing commas. Replaced with hand-written state machine.
  • AND/OR precedence: initially parsed as same level, gave wrong results for a>1 OR b>2 AND c>3. Fixed by splitting into parse_or/parse_and levels.
  • NULL in ORDER BY: comparing None with int crashes. Wrapped sort keys in (type_group, value) tuples.
